# Invitation identity and link recovery

**Status** Implemented and verified locally across all three phases. See 2026-11-18-invitation-identity-and-link-recovery-notes.md for the tested candidates, checks and rollout sequence.

**Baseline** `develop` at `03df6feb973f46e445c46bee0a818dffb0af323d` in `/Users/juan/code/layalga`, with a pre-existing `AGENTS.md` edit (blob `f7edb62a6189e9704f6ee68f0032b5d4a241c051`).

## Outcome and scope

- **SE-H1.** Two unrelated parties can have the same displayed name and separate invitations, guest accounts, visit histories and memory. To invite a returning party, the host explicitly chooses its existing record.
- **FE-H1.** After an invitation capture completes, its creator can copy the link from the progress screen or reopen it from the dashboard after navigation or reload. Repeated reveals of a new capture return the same link while it remains valid. An older hash-only link can be replaced after the host confirms the effect.
- Scope covers these two findings from the November 18 [visitor review](../agents/2026-11-18-visitor-check/pre-launch-report.md). Atomic association of a capture with its run addresses the part of BE-M1 that would otherwise make link recovery ambiguous. The rest of the audit, dependency upgrades, historical identity repair, guest email activation and any production action stay outside this plan.

## Current behavior

- The database requires unique `(home_id, family_name)`. Capture looks up the exact name and reuses the first party. Separately, the worker guesses the memory party from the invitation wording before calling the model. The Google claim and visit account authorize by party ID. Once two families share that ID, account SQL cannot distinguish them. [Uniqueness](../../supabase/migrations/20260831000100_core.sql#L31), [Capture](../../src/core/booking/invitations.ts#L113), [Memory authority](../../src/agent/run-task.ts#L967), [Claim](../../src/lib/auth/party-claim.ts#L6), [Guest visit access](../../src/lib/auth/guest-account.ts#L42), [Cancellation](../../src/app/%5Blocale%5D/visits/actions.ts#L43).
- The dashboard retains the exact run ID in client state. Its server action joins the run and its capture audit event, then rotates the invitation token to reveal a link. The separate status route only shows the run. The token in the database is a hash, and run payload and result text are scrubbed on their retention schedule. [Capture UI](../../src/components/host/capture-invitation-form.tsx#L62), [Reveal action](../../src/app/%5Blocale%5D/%28host%29/actions.ts#L72), [Status route](../../src/app/%5Blocale%5D/runs/%5Bid%5D/status/page.tsx#L13), [Token lifecycle](../../src/core/booking/invitations.ts#L188), [Retention](../../supabase/migrations/20261015084815_drop_demo_schema.sql#L43).

## Design choices

| Decision                                                                                                                                                                                                                                                                 | Alternatives and trade-off                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Default to **New party**. Let the host select an existing record by ID, with recent invitation and stay dates for context. Use the same verified ID for capture and optional memory recall.                                                                              | Surname matching is convenient and cannot establish identity. Always creating a new record would isolate families but lose continuity for known returning guests. The host chooses New when they cannot identify a matching record.                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Use a separate task discriminator for captures with an explicit party choice. Keep legacy tasks readable with safe new-party semantics. Remove name uniqueness only after Web and AgentCore both support the new behavior.                                               | Adding an optional property to the old task shape is smaller but its parser can strip it on the older runtime. The new task is rejected by old workers instead of changing the selected party silently. [Current task parser](../../src/agent/task.ts#L24), [Queue reader](../../src/agent/queue.ts#L59), [Claim-time revalidation](../../src/agent/run-task.ts#L234).                                                                                                                                                                                                                                                                                    |
| Recover the current URL for new captures using a versioned, purpose-separated HMAC with an invitation ID and a random generation. Keep hash verification for guest access. For legacy random tokens, offer a confirmed replacement and make the replacement recoverable. | An explicit replacement for every reveal preserves hash-only storage but breaks any previously shared URL and email capabilities bound to it. An encrypted bearer copy introduces separate ciphertext and key handling. Derivation introduces the ability for the trusted server to reconstruct **new-format** links using its existing secret and DB metadata. This is a deliberate change to the current lifecycle policy and must be documented. [Current lifecycle policy](../security/data-lifecycle.md#durable-execution-metadata), [Node.js HMAC API](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptocreatehmacalgorithm-key-options). |

## Phases and rollout

| Phase                                                                                             | Deliverable                                                                            | Evidence to accept                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| [1. Explicit party choice](2026-11-18-invitation-identity-and-link-recovery-phases/phase-1.md)    | Host choice, shared task and authority contract, safe behavior with the current schema | A selected returning party retains its account and recall. Legacy and new-party capture cannot reuse a name match. The old parser rejects the new task.            |
| [2. Allow shared names](2026-11-18-invitation-identity-and-link-recovery-phases/phase-2.md)       | Constraint migration and identity isolation tests                                      | Two distinct parties with the same name can claim and manage only their own fixture visits. Previous records and links remain valid.                               |
| [3. Recover a completed link](2026-11-18-invitation-identity-and-link-recovery-phases/phase-3.md) | Durable capture outcome, link reveal on status and dashboard recovery                  | Reload and concurrent reveals keep the exact same link. Legacy replacement requires confirmation. Unauthorized, expired and cancelled cases never return a bearer. |

Accept each phase in order. Local implementation can proceed in sequence after separate authorization. Production release authority is separate. The compatible Phase 1 web and AgentCore artifacts must precede Phase 2's constraint removal. Verify both identities and a synthetic capture through the serving AgentCore DEFAULT endpoint under the existing release workflow. After name duplicates exist, the minimum rollback candidate is the safe Phase 1 behavior. Phase 3 has its own web-first compatibility cutover. Use the existing rollout playbook and runtime version preflight.
