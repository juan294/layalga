## What a guest can book

A first-time guest can find the household by name and say, “We’re two adults looking for two weeks in July.” The system asks for missing details, checks the room ledger and replies with feasible check-in and checkout dates and guest-facing room choices. The guest can compare stays, select exact rooms, add requests and submit their choice. The receipt says **Awaiting host confirmation**. Up to that point Juan and Jordan do nothing for this booking.

Either host sees one complete request. If they will be home and want to host, one approval rechecks current availability and confirms the exact stay. The guest can retrieve the outcome without anyone sending an invitation, copying a link, or asking them to book again. If the host declines, or the rooms have gone, the system tells the guest and offers the next available action. Inventory availability is computed. The host supplies the final judgment about being home.

**Owner decisions.** Anyone may find the household by name and ask. Guests interact with the system, see feasible dates and rooms and make their own selection before a host is involved. The only human hosting decision is at the end. The earlier research described questions that were open at the time (`docs/research/2026-11-21-guest-initiated-stay-requests.md:30`); this clarification settles the disclosure of feasible stays and the effect of approval.

## Design choices for review

| Choice | Selected behavior and trade-off |
| --- | --- |
| Public availability | Publish guest-facing room facts only for feasible options at a listed home. Show the requested date window, rooms and sleeping arrangements. Keep hosts’ whereabouts, other stays, contact details, raw occupancy and private notes out of public responses. A guest can book an appropriate fit while household members retain control over the final decision. |
| Waiting for a reply | A submission records the exact proposal and reserves no rooms while waiting. An inventory hold at this point would allow unanswered public requests to tie up the house. The guest sees that availability can change. One atomic recheck at approval decides competing requests. |
| Guest identity and reply | Proposed default: browse anonymously, sign in with Google when submitting and return to a private status page or ask in the guest conversation. This uses the existing identity provider without needing a first invitation. An email-link alternative would require a separate pre-booking verification and recovery flow. |
| Existing invitations | The final-decision rule applies to the new, guest-initiated flow. A host who proactively issues an invitation still starts the existing journey. Changing approval rules for those invitations would be a separate product decision. |
| Channels | Deliver the booking operations, an English/Spanish conversation on the site, and page-scoped WebMCP. An independently installable ChatGPT app remains the follow-on described by the owner. Share callable booking logic across channels. ChatGPT account linking, a remote MCP endpoint, native client tests and directory submission have their own scope. Local Supabase OAuth-server support is presently disabled (`supabase/config.toml:376`). |

## Phases and acceptance

| Phase | Demonstration required before acceptance |
| --- | --- |
| [1. Find the household and compare stays](2026-11-21-self-service-booking-phases/phase-1.md) | A stranger discovers the listed home and sees 14-night stays with available guest-facing rooms. Hidden homes and private household data stay undisclosed. |
| [2. Submit a stay and track the reply](2026-11-21-self-service-booking-phases/phase-2.md) | A first-time requester submits a selected stay, receives one receipt and can retrieve it privately. The hosts see one pending item. The room remains available. |
| [3. Confirm with one host decision](2026-11-21-self-service-booking-phases/phase-3.md) | One host action commits exactly one confirmed visit, exact-room occupancy, calendar eligibility and the scheduled follow-up. The guest has nothing else to submit. A competing booking produces fresh choices. |
| [4. Complete the journey in conversation](2026-11-21-self-service-booking-phases/phase-4.md) | A guest uses ordinary language to search, refine, select, submit and check the outcome. WebMCP and the page use the same services. Tests include closing/reopening the session and continuing after a failed search or unavailable model. |

**Lifecycle.** A public lookup has no side effects. An explicit guest submission moves a new request to pending. Pending can end in confirmed, declined, withdrawn, expired or needs-new-selection. A settled outcome is stable on replay. A changed selection has a new reviewable version and invalidates the previous host action. Confirmation exposes the existing post-booking visit state, including later reconfirmation and cancellation. The lodging dates use a half-open check-in/checkout interval in the household's timezone. See the existing guest flow and confirmation effects at `src/core/booking/guest-actions.ts:112` and `src/core/booking/holds.ts:309`.

## Stuck states and recovery

| Condition | Visible outcome and recovery | Automated proof |
| --- | --- | --- |
| No matching home, no dates, ambiguous dates, or insufficient capacity | Guest can correct the name, window or party. Return alternatives only from a new successful ledger search. | Phase 1 fixtures cover private and similarly named homes, adjacent stays, no fit and a revised search that succeeds. |
| Login interrupted, duplicate submit or pending limit reached | Preserve the visible selection through an ordinary retry. Show an existing receipt on replay. A guest at the limit can view and withdraw pending requests. Stale terms require fresh guest review. | Phase 2 cancel/resume login, lost response, concurrent submits and withdrawal tests. |
| Host has not replied, or the notification failed | Guest sees pending and can return or withdraw. The host sees the request on their dashboard; configured pings use existing retry handling. A past check-in closes the request with a new-search action. | Disable mail, exercise a failed send and advance the household clock. Verify both views and action eligibility. |
| Host declines, term changes or another guest takes the room | Guest sees the outcome and can find another stay. Host sees whether approval took effect. No automatic alternate room, date or overflow consent. | Phase 3 concurrency tests assert one actual booking and a recoverable result for the other requester. |
| Interrupted approval, repeated click or conflicting host answers | Roll back incomplete booking work. Host can retry a transient error or reload the recorded outcome. A disconnected guest can reopen their private receipt. | Force a database fault before commit and a lost response after commit. Assert repeat-safe visit, occupancy and chase-job counts. |
| Conversation unavailable, WebMCP missing or notification delivery uncertain | Guest can continue with structured controls and check the stored decision. Report delivery as a separate state. | Phase 4 interpreter-failure, unsupported-browser and authenticated status tests. |
