# Guest-initiated stay requests and public household discovery

**Owner decision, 2026-11-21.** Anyone should be able to find the household by name and ask for a stay, including someone who has never received an invitation. The intended channel is a future ChatGPT app. The example is a guest asking, “Could we stay at L’Ayalga for two weeks in July?” Public discovery and permission to ask are settled. This decision does not specify what availability a stranger may see or when the household agrees to particular dates.

**Current answer.** Today the first in-app step is a host creating an invitation. An interested guest can ask the hosts outside L’Ayalga, and a host can enter that conversation as an invitation, but the original inquiry has no record, receipt or reply path in the app. The guest has no way to tell L’Ayalga which home they want to contact. Once invited, the guest can already search for 14 consecutive nights, choose rooms and submit a stay. The missing journey runs from finding a household through receiving its answer. ## What guests can see, retry and recover

Before an invitation exists, the current public experience reveals no household availability. Guest search derives its home from a valid invitation token or a verified return session. Even invited guests receive only guest-facing room facts. Other guests’ identities and private household notes stay out of search results. The public privacy notice currently describes a private coordinator for one household and the handling of invitations, bookings and reminders. It does not describe public household discovery, prospective inquiries or ChatGPT as a recipient. (`src/app/[locale]/g/[token]/actions.ts:40`, `src/app/[locale]/guest/actions.ts:41`, `docs/security/data-lifecycle.md:56`, `docs/security/data-lifecycle.md:68`, `messages/en.json:42`, `messages/en.json:50`)

The current recovery paths start after the host acts. Capture replay checks the submission identity and payload to avoid creating a second invitation. A host can retry an eligible failed capture, recover the same active link from history, or review replacement of a legacy link. A guest with an expired or revoked link sees instructions to contact the host. The host decision screen can retry the application of a recorded decision. None of these gives a guest a receipt before invitation, lets them withdraw an unanswered inquiry or tells them whether a second message duplicates the first. (`src/agent/run-task.ts:770`, `src/core/booking/invitations.ts:130`, `src/components/host/capture-invitation-form.tsx:372`, `docs/guides/host-manual.md:43`, `messages/en.json:329`, `src/components/host/pending-decisions.tsx:150`)

## What this unlocks for ChatGPT

**Product implication.** A guest who discovers L’Ayalga in ChatGPT has no useful first booking action today unless a host previously invited them. Public lookup and the ability to ask for a stay would give that person a reason to use the app immediately. The existing booking flow becomes relevant once the guest has authority to search or book. The earlier channel research found only page-scoped WebMCP tools and an internal task endpoint in this checkout. Neither takes a first inquiry from ChatGPT. (`docs/research/2026-11-21-conversational-booking.md:32`, `src/components/webmcp/guest-tools.ts:43`, `src/app/api/agent/run/route.ts:11`, `docs/roadmap.md:36`)

**External platform facts, checked 2026-11-21.** OpenAI calls the distributable package a plugin. ChatGPT can call a remote MCP server over HTTPS and use its structured results directly in conversation. Its guidance distinguishes a public read, such as finding a household that has made its name public, from doing something on a user’s behalf. Persisting or sending a stay request is a write even if it reserves no rooms. OpenAI documents OAuth 2.1 for authenticated MCP actions. Public distribution also requires a verified publisher, plugin submission, review and publication. These are capabilities and requirements of the platform. A working inquiry flow alone would establish neither a ChatGPT connection nor a directory listing. [MCP server guide](https://developers.openai.com/plugins/concepts/mcp-server) · [Authentication](https://developers.openai.com/plugins/build/auth) · [Tool annotations](https://developers.openai.com/plugins/plugin-guidelines) · [Submission](https://developers.openai.com/plugins/deploy/submission)

## Decisions still open

1. **What may someone see before asking?** The owner has approved finding the household by name. Public profile details, approximate availability and exact room or date information are distinct disclosures. Today's guest search covers the last two only within an invitation. (`src/core/booking/guest-actions.ts:84`, `docs/security/data-lifecycle.md:58`)
2. **How can a first-time guest receive an answer?** The app has no pre-invitation identity or return channel. The choice affects whether someone must link an account to send, how they check later, and how they withdraw a request or recognize a duplicate. Existing guest reminders require an invitation and their own consent. (`src/app/auth/callback/route.ts:28`, `src/core/db/schema.ts:624`)
3. **What does the host’s “yes” mean?** Permission to see dates and choose rooms leaves the current booking checks intact. Acceptance of a specific stay carries an additional promise about rooms and dates. Existing decisions resume interrupted tasks, and availability is checked again before confirmation. The owner has selected guest initiation but has not yet assigned an effect to this first host response. (`src/core/decisions/host-decision.ts:16`, `src/agent/policy-hook.ts:111`, `src/core/booking/holds.ts:275`)
